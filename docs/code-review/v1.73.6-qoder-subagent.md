## 发现

审查者逐条追到源码后，**未发现 P0 / P1**。给出 3 条 P2 + 1 条 P3 + 3 条待议。

### P2-1 | `Selftest+ScanDiagnostics.swift` 的 lint 只钉「扫到多少文件」，不钉「命中多少调用」→ 匹配逻辑退化即在空集上恒真通过

- **症状 → 后果**：`mustBeThere` + `files.count >= 50` 两个下界只约束"扫到的文件数"；若
  `t.contains(".enumerator(")` 这个模式将来被改坏、匹配集退回 0，`offenders.isEmpty` 依然为真，
  绿灯被读成"全仓干净"——正是 v1.73.6 第一版踩过的空集假绿的同类软肋。
- **处置：已修**。新增"活性证据"两道：`matchedCalls < 8` 直接判红（当前产品源码非 atPath 的
  `.enumerator(` 实测 11 处），并对 `mustBeThere` 里每个文件断言各自至少命中 1 处。
  **按新增"变异验证要改坏正则"这条补测**：把匹配模式临时换成 `.enumeratorZZZ(`，
  自检如期因命中数下界变红（613/1），还原后回绿。

### P2-2 | lint 的 12 行 `span` 窗口会把邻居遍历的 `recordDeniedAccess`、或文档注释里出现的这个词算作满足 → 误豁免

- **症状 → 后果**：判据是"本行起往下 12 行拼起来含 `recordDeniedAccess`"。若某处确实漏了记账，
  但其后 12 行内恰有**另一处**遍历的 `recordDeniedAccess`（或 handler 上方注释写了"要调用
  recordDeniedAccess"），本行会被误判合格。现状 9→11 处各自 handler 紧随、彼此相隔 >12 行，
  故**当前 0 误豁免**；但这是防回归闸的软肋——恰在"新写一处紧挨着的漏网遍历"时可能放过。
- **处置：已修**。窗口右端改为切在"下一处非注释 `.enumerator(` 之前"；且窗口内**先按物理行
  过滤掉以 `//`/`///` 起头的行**再判断，杜绝注释里的词替漏网实现背书。同时把"有 `errorHandler:`"
  与"handler 体内有 `recordDeniedAccess`"拆成两条独立 offender。
  **变异验证**：把 CLICacheScanner 的 handler 体里 `FileSystem.recordDeniedAccess(...)` 实删、
  只在一句注释里提及该词——lint 变红（613/1）；还原回绿。这条正是审查者点名的软肋被实测封住。

### P2-3 | `CLICacheScanner` / `SpotlightScanner` 补了 `recordDeniedAccess` 留痕，但只返回 `(size,count)`，调用方按 `size>0` 仍会默认勾选 → 被掐断的子树仍报成"小而自信的体积"

- **症状 → 后果**：这两个 `calculateDirectoryStats` 不像 AudioHAL/PrinterDriver 有 `readable` 契约，
  一次只读到一半的目录，界面照样显示一个偏小的确定体积并默认勾选。
- **审查者自己追删除链的结论**：清理动作是按缓存根的**直接子项整条**走网关删除，与 size 无关；
  size 只影响展示与"是否 >0 才列项"，**不会因截断而多删**——属求体积口径失真而非误删，
  与本轮 README 的表述（对这两处只承诺"记进盲区"、不承诺 `readable`）一致，故不构成 P0/P1。
- **处置：转下一轮 / 记待议**（见下）。本轮不扩范围，README 已如实限定口径。

### P3 | AudioHAL:512 / PrinterDriver:509 移除 `= true` 默认值本身安全，但依赖编译器兜底

- 全部调用点（生产 PrinterDriver.swift:236-238、AudioHALScanner.swift:364-366 + 各自检）均已
  显式传 `metrics.readable`/`metricsReadable`，漏传即编译失败，无残留默认路径。
- **处置：不单独动作**（"默认值即安全策略"的参数被刻意去掉默认，方向正确；由 tsc 兜底足够）。

## 未发现 P0/P1：逐条追到代码并确认没问题的点

- **`readable=false` 是否真拦住默认勾选（审查项 C）——真拦得住**：
  - PrinterDriver：内联 `guard metrics.readable else { … isSelected:false }`（:221-234）在下钻
    `evaluateDriverEntry` 前短路；`evaluateDriverEntry` 内 `guard metricsReadable else → .needsConfirmation`
    （:524）位于 `size==0 → .corrupted`（:534）之前；PPD 分组 `group.unreadable → isSelected:false`
    （:426-428,463）；`clean()` 只放行 `isOrphanOrCorrupted`（:603）。四道一致。
  - AudioHAL：`guard metricsReadable else → .unknownNeedsConfirmation`（:537）在任何 orphan/corrupted
    结论前；缓存分支 `guard metrics.readable, metrics.size>0 else { continue }`（:423）；`clean()` 同闸（:600）。
  - 反证自检到位：`Selftest+PrinterDriverDeep.swift:150-154` 用 `size:0, metricsReadable:false`
    断言必须 `.needsConfirmation` 而非 `.corrupted`——能证伪"guard 顺序被改回"。
- **`WalkBlockFlag` 时序/竞态（审查项 D）——正确**：`set()`/`value` 各持 `NSLock`；errorHandler 由枚举器
  在迭代线程同步回调，`blocked.value` 的读发生在整个循环之后，全部 set 先于该读，无漏读无竞态；
  `return true` 仅表"继续遍历"，每次拒绝幂等置位，与继续语义无冲突；`@unchecked Sendable` 由内部锁支撑成立。
  TSan 自检零 `WARNING: ThreadSanitizer`。
- **lint 能否变红（审查项 A）**：能（见 P2-1/P2-2 的两例变异）。`atPath:` 按同一行判定、不被邻居误豁免。
- **mode-000 行为自检可证伪（审查项 F）**：① CLICache 断言盲区清单含 locked 路径（删 handler 即红）；
  ② AudioHAL 断言 `.readable==false`（不接 blocked.value 即红）；③ 反证干净树 `readable==true && fileCount==2`
  （把 readable 焊死 false 即红）。三条皆可红。
- **两处 `errorHandler:{_,_ in true}`（ColorSync:291、Duplicate:482）补 `recordDeniedAccess`**：
  从"有 handler 但静默丢子树"升级为真留痕，方向正确。
