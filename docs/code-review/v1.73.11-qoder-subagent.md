## 2. 为什么这个缺陷是真的（实测，不是推理）

`enumerator(atPath:)` 这个重载**没有** `errorHandler` 参数。在合成夹具上实测
（`nested/` chmod 000，里面放一个 `.ips`）：

```
A) 旧写法 enumerator(atPath:)   yield: ["aaa.log", "zzz.log", "secret"]      错误回调：无
B) 新写法 enumerator(at:errorHandler:)  yield 同样 3 条，但 errorHandler 如实回调
                                        denied: ["<root>/secret"]
```

即：**返回的是合法枚举器**，被拒子树被静默跳过，既不报错也不产生 issue。
于是面板指着少了报告的清单说"这就是全部崩溃报告"——正是本仓反复收编的"读不到 ≠ 没有"那一族。
旧 lint 要求"nil 分支必须上报 unreadable"，而 nil 根本不是这一族的失效模式，
所以 `DiagnosticReportScanner:105` 在它眼皮底下过了三个版本。

**真机侧本机无差异**（诚实记录）：`/Library/Logs/DiagnosticReports` 69 条、
`~/Library/Logs/DiagnosticReports` 148 条，两种写法条目数相同、被拒子项 0——
这台机器的这两个目录是平铺可读的。收口的价值在"别的机器/别的权限布局上不再静默截断"，
不在本机数字变化。

## 5. 两个必须说出来的操作性风险

1. **发版门禁会被计时哨兵抖动卡住**：本轮两次全量跑分别得到 34 与 35 条失败，多出的
   `卸载器：已安装 App 清单并行取体积（宽上界…）` 是**墙钟上界**断言，在其它 App 占着
   90%/82% CPU 的机器上会翻。新的基线比对机制（名集必须一字不差）会把这种假红变成
   **发版拦阻**。方向是对的（假红也比假绿好），但这类断言应当尽快改成同负载缩放比
   （`RELEASE-CHECKLIST` §"活性证据"已有先例）。
2. **本机 UI 契约仍只能靠纯判据 + 源码接线**：本轮把 `unreadablePositionCount` 也照此抽出。
   真机界面走查（含 v1.73.10 那批卡片改动）**仍未做**，等用户空闲时补。
