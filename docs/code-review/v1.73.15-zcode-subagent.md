## 2. 发现

**未发现 P0 / P1。** 以下为 P2 / P3。

### P2-1　Mail Downloads 根内名为 `Attachments` 的子目录其文件被收集两次（体积双计、条目重复）

- **严重度**：P2（触发面窄的角落布局；不构成误删——网关对同一路径的第二候选拦在"祖先已删"静默去重上）
- **位置**：`Sources/MacClean/MailAttachmentsScanner.swift:121-140`（`collect` 主循环 + `pendingAttachmentsDirs` 二次收集）
- **症状**：`collectsRootFiles == true` 的根（Mail Downloads）里，主循环把**所有**普通文件（含子目录内的）逐条 `appendItem`；同时子目录若名为 `attachmentsDirName`（"Attachments"）又被推进 `pendingAttachmentsDirs`，第二个循环 `filesUnder` 把同一批文件**再收一遍**。变异实测：夹具根下建 8192 B / 2048 B 两个文件、再建一个含 1024 B 文件的子目录 `Attachments`，`scan()` 返回 **items=4、total=12288**（应为 3 项 / 11248 B）。附带两处后果：`Summary.items` 出现相同 `id`（即同一路径）的两条，`MailAttachmentsView` 的 `ForEach(model.summary.items)`（id 即路径）会拿到重复 id；选中其一清理时网关只记一次，界面"已选 N 项 / 体积"与结果对不上。
- **为什么是问题**：同一轮声明的收集语义是"根的收集语义由 `MailRoot.collectsRootFiles` 结构声明，不用路径后缀字符串猜"，但 `Attachments` 目录名判据没有和 `collectsRootFiles == true` 的分支互斥，两个收集通道在同一根上叠加。触发条件（Mail Downloads 下恰好有名为 `Attachments` 的子目录）不常见，但一旦触发就是呈现侧体积失真 + 重复行。
- **建议动作**：`isMailDownloads == true` 时不再把名为 `Attachments` 的子目录推进 `pendingAttachmentsDirs`（或 `appendItem` 前按 path 去重）；并在现有 Mail 套件的夹具里补这个形状让两分支互斥有断言可证伪。

### P2-2　`MailAttachmentsScanner.clean` 没有"合法路径集复推"——与同轮 BrowserPrivacy 的威胁模型不一致

- **严重度**：P2（纵深防御缺口，非当前可利用路径；网关仍拦 G6/G8/白名单、默认 toTrash）
- **位置**：`Sources/MacClean/MailAttachmentsScanner.swift:195-201`
- **症状**：`clean(items:)` 把任意 `AttachmentItem.path` 直接映射为 `Candidate(domain: nil)`，没有模块侧"该路径是否为本模块登记的两个根/其下结构"的复推。对照同轮 `BrowserPrivacyScanner.clean` 的第④道拦截（`Sources/MacClean/BrowserPrivacyScanner.swift:281-289, 379-390`）：那边明确论证过"网关的主目录放行挡不住'夹带一个家目录路径'"并按 `outsideDomain` 拒绝——同一论证完全适用于 Mail 侧（附件路径同样在主目录内）。
- **为什么是问题**：两个同轮模块对"调用方拼装条目"这一威胁的防线一高一低；编译期可拼装的 `AttachmentItem` 可以把家目录内任意路径送进删除管道（仍受网关护栏约束，故非 P0/P1）。缺口不在今天的 UI（只传 `filter(\.isSelected)` 的扫描产物），而在模块契约本身。
- **建议动作**：照 BrowserPrivacy 同型补一道：clean 时刻按 `rootsOverride ?? defaultRoots` 重推合法路径集（Mail Downloads 根文件 / `Attachments` 目录内文件），夹带路径按 `outsideDomain` 拒并逐条带原因。

### P2-3　「Safari History 删除必被网关拒」的判据前提（History.db ∈ G6 硬排除清单）没有任何断言钉住

- **严重度**：P2（缺前置锚，非当前错误）
- **位置**：`Sources/MacClean/BrowserPrivacyModels.swift:188-192`（注释把"在 G6 硬排除清单里"当既定事实）；清单本体 `Sources/MacClean/CleanPaths.swift:13`
- **症状**：模块行为与文档（`docs/research/mainstream-parity.md` Privacy 行"删除被网关拒并原样展示"）都依赖 `~/Library/Safari/History.db` 留在 `CleanPaths.hardExclude` 里。全部自检（含本轮 14 条）没有任何一条断言 `FileSystem.isHardExcluded(展开后的 History.db)`；若该清单条目日后被移除，扫描侧 G6 注记消失、格子变为可勾、网关放行删除真实浏览历史数据库，而自检照绿。对比：本轮 G18 条自己就给 `/System/Applications` 补了 `isSystemProtected` 前置断言，同样手法没有用到 G6 这条上。
- **为什么是问题**：被声明为安全语义的事实（"对清单服从而非缺陷"）建立在外部清单的一行上，却没有可证伪的锚——清单漂移是静默的。
- **建议动作**：BrowserPrivacy 套件补一条前置断言：`FileSystem.isHardExcluded("~/Library/Safari/History.db" 展开)`（`Bookmarks.plist` 同理），清单变更时先红在这里而不是静默放行。

### P3-1　「全选唯一判据」存在两份平行表述，其中一份生产不可达
