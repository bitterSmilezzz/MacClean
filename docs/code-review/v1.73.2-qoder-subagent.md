## 第二轮发现与处置

第二轮复核确认第一轮的 7 条里 5 条**已修**、2 条**修得不完全**，并对本轮新写的断言重新做了变异。

### [P1] 本轮标题性修复（`restore` 不再整片写回）零断言：退回旧写法后自检照样全绿

- 处置：**已修**。新增「撤销快照 restore：不得退回『开头读一份数组、结尾整片写回』的形状」——
  以 `var sessions = load()` 与 `save(sessions)` 在文件内各只出现 1 次（都在 `mutate` 内）作为形状指纹。
- 变异验证：把 `restore` 退回旧写法 → 该断言变红并打印 `load 2 次 / 整片 save 2 次` ✔。
  （行为级反证需要"restore 期间恰好有 record"的时序夹具，第二轮评估为易脆，故采用形状断言 +
  下面那条落账失败断言组合覆盖。）

### [P2] `append` 改成"返回锁外重读磁盘的结果"——写失败时连界面上那一行证据都没了（本轮引入的退化）

- 处置：**已修**。`mutate` 自己返回合并后的列表，`append` 不再回读磁盘；写失败时返回值仍含
  刚记的那条。`save` 改为 `do/catch` 返回 Bool。
- 变异验证：把 `append` 改回 `return load()` → 「状态目录不可写时…」变红 ✔。

### [P2] `clear()` 的"盘上真的写掉了"核验零断言

- 处置：**已修**。新增用只读状态目录（`chmod 0555`）夹具的断言：写失败时 `clear()` 必须返回 false、
  `append` 的返回值仍含新那条、而磁盘上确实没有它。
- 顺带订正一处**注释里的事实错误**（第二轮实测）：`.atomic` 是"同目录建临时文件再 rename"，
  只看**目录**写权限；我原先写的成因"history.json 属主变 root 导致 EPERM"不准确——
  实测文件改只读仍写得动，目录 0555 才失败（NSCocoaError 513）。注释已改准。

### [P2] `restore` 落账可静默丢弃：文件已搬回原位、快照仍标未还原，用户再点永远报"失败"且不收敛

- 处置：**已修**。`mutate` 返回是否落盘，`restore` 在"没找到会话"或"写失败"时往
  `result.errors` 追加"文件已放回原位，但撤销快照未能记账"。
- 新增断言：只读目录夹具下跑一次真实 `restore`，断言搬运成功**且** errors 里带出记账失败 ✔。
- **残余（转待议）**：`HistoryView` 那行的状态显示仍只有"可放回 / 已放回"两态，落账失败时
  视觉上仍是空白，靠 toast 播报。判据要改成"`canRestore == false` 且有已还原项"，属 UI 改动。

### [P2] 字面量 lint 有三种合法绕法（换行链式 / 不带括号取函数 / typealias），且 `save` 是 internal

- 处置：**已修**（按建议换成编译期保证）：两个 `save` 降 `private`，自检的 18 处裸写盘复位
  改走新增的 `replaceAllForSelftest`（也经过事务锁——原先那 8+ 处是在**被测锁外面**复位状态的）。
  lint 保留为兜底，matcher 去掉尾括号并加上 `replaceAllForSelftest`。

### [P3] `mutate` 把"只保留最近 100 次"这条 `record` 的策略加到了 `restore` 的落账上

## 第三方会话的增量 review 提出的、本轮一并处置的条目

本轮工作树期间，另一个 agent 会话在 `docs/code-review/2026-09-24-0446.md` 对同一批未提交改动
做了一次增量复审，提出一条实质问题，我自己核实后确认成立并一并修掉：

### [P1] 6 个写入口里 5 个丢弃了 `append` 的返回值 → 治理卡片记的账在界面上看不见

- 核实：`AppState.history` 只在 init、`recordClean`、`clearHistory` 三处被赋值；删除网关、
  下载/截图归档、硬链接去重、定时自愈全部直接 `HistoryStore.append` 且不回看返回值。
  `HistoryView` 与 `SidebarView` 读的都是 `app.history`。
- 症状 → 后果：用任一治理卡片清理后，记录**确实落盘**，但历史页与侧栏计数仍停在旧内容，
  用户走不到那一行的「放回原位」——本轮主张的"记录在 = 可回退"在显示层断掉。
  这不是本轮引入的（本轮之前更糟：那份陈旧缓存还会把记录整片抹掉），但本轮把
  `append` 设计成"返回合并后的清单供调用方刷新缓存"，5 个调用点却全都丢掉了它，
  等于修复只接了一半。
- 处置：**已修**。`AppState.reloadHistory()` 从盘重读，`refreshDisk()` 里顺手调一次
  （每个治理卡片清理完都会走 `onTriggerClean → refreshDisk`），`HistoryView.onAppear`
  再兜一次。新增断言「历史可见性：别的模块直接 append 的记录，刷新后必须出现在 app.history 里」，
  并故意在断言里先验证"刷新前确实看不见"。
- 变异验证：把 `refreshDisk()` 里的 `reloadHistory()` 删掉 → 该断言变红 ✔。
- 实机验证：`dist/MacClean.app` 打开「清理历史」，侧栏计数与页面"共 N 次清理"一致、
  趋势图/分布/记录列表均正常渲染；未触碰「清空记录」。
