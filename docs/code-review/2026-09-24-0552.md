### P1 — 重要

- **`Sources/MacClean/DownloadsOrganizerCard.swift:389-403`（`executeArchive`）与 `Sources/MacClean/ScreenshotsOrganizerCard.swift:401-416`（`executeArchive`）** — 归档路径写历史但不触发刷新，上一轮 P1 的同一缺陷类残留 2 处
  - 为什么是问题：`onTriggerClean?()` 在这两个卡片里**各自只有一处**调用点，都在 `executeClean()`（`DownloadsOrganizerCard.swift:384`、`ScreenshotsOrganizerCard.swift:396`）。而**归档同样会写历史**：`DownloadsOrganizerScanner.swift:282` 与 `ScreenshotsOrganizerScanner.swift:268` 都会调 `recordArchiveMove(...)`，后者落到 `DownloadsOrganizerScanner.swift:303` / `ScreenshotsOrganizerScanner.swift:326` 的 `HistoryStore.append`（`mode: "归档移动"`）。`executeArchive()` 的完成回调里只有 `loadData()`，**没有** `onTriggerClean?()`，所以：用户点「智能归档到 ~/Pictures/Screenshots_Archive」或归档下载 → 记录**已落盘** → 但 `AppState.history` 停在旧值 → 切到「清理历史」页看不到这条「归档移动」，侧栏计数也不变，直到下一次别的清理、分类扫描或重启。这与上一轮报的缺陷在用户可见层面完全同型，只是范围从「全部治理卡片」缩到「归档」这两条路径。无数据丢失（盘上是全的），故仍定 P1。
  - 建议：在两个 `executeArchive()` 的 `DispatchQueue.main.async` 块里补 `self.onTriggerClean?()`（与 `executeClean` 对称）。更彻底的做法是让 `recordArchiveMove` 这一层统一发一条 `NotificationCenter` 通知、由 `AppState` 订阅刷新，这样新增写入口不会再漏——现有写法每加一个写路径就要记得在 UI 侧配对一次，而这次的漏配正说明该约定靠人记不可靠。另建议把 `Selftest+SystemAndHistory.swift` 那条自检扩成「逐个写入口写一条、断言 `refreshDisk()` 后都可见」，或直接在归档路径上加一条用例。

- **`Sources/MacClean/Scanner.swift:1675`** — `modificationDate: verdict.lastUsed` 是冗余实参，且上方注释对旧行为的断言与实现不符
  - 为什么是问题：两层。(1) **冗余**：`scanLargeFiles()` 的返回值在 `Scanner.swift:153`/`:358` 之后立刻经过 `filtered.map { annotateUsage($0) }`（:167 / :372），而 `annotateUsage`（:388-391）对单路径项走的就是 `FileSystem.usage(of: item.path)`——与 `staleDownloadsVerdict` 内部的调用**完全同一个函数、同一个入参**，随后 `copy.use = UseState(...)` 把它整个覆盖掉。所以构造时传的 `verdict.lastUsed` 在几微秒后就被同值覆盖，是纯粹的冗余。(2) **注释断言不成立**：新增注释写「旧写法 `lastUsed` 为 nil，面板一个日期都不给」——旧写法同样经过 `annotateUsage`，`use.lastUsed` 并非 nil；即便为 nil，`CleanItem.modificationDate`（`Models.swift:265-268`）也会回退到 `FileSystem.modificationDate(path)` 现场取 mtime。所以「一个日期都不给」这个前提是错的，而它正是这次多传一个参数的**理由**。
