### [P1] 文档宣称"偏好碎片模块也有源码接线自检"，实际一条都没有；README 进一步放大成"每个治理模块"

- 位置：`README.md` 功能段与 G14 表行、`docs/CLEANUP-RULES.md` G14、`README.md` 测试策略段；缺失处应为 `Selftests/Selftest+PreferenceResidueDeep.swift`
- 症状 → 后果：三处文档都写"两个模块各有源码接线自检守着"，但 `SelftestSource.read` 当时只有 5 个调用点，`PreferenceResidueInspector` 与 `Uninstaller` 都不在其中。G14 因此被写成"不再只靠人 review 维持"，而**恰恰是历史上唯一一处连 `isSafeToClean` 都没调、调用方还是 App 卸载器的那条路径仍然只靠人 review**。后果不是当下误删，是把一条不存在的护栏写进了公开文档并当作既成事实。
- 处置：**已修**。补 `Selftest+PreferenceResidueDeep.swift` 的「偏好碎片清理：源码接线——无裸删除、卸载器保留记账」；并把 `README.md` 测试策略段的"每个治理模块"改成如实的 **5 个模块**（开发工程产物、偏好碎片、ColorSync、打印机驱动、音频 HAL）+ 明写"其余模块仍靠清单里那条 grep 人工核对"。
- 变异验证：在 `Uninstaller.swift:480` 偷偷加 `journal: .none` → 该断言变红 ✔。

### [P2] 确认框与 README 承诺"逐项说明原因"，UI 只给聚合计数，`outcome.rejected` 被整个丢弃

- 位置：`DevProjectInspectorView.swift` 确认框 message、`PreferenceResidueInspector.swift` 的元组塌缩、`Uninstaller.swift` 摘要
- 症状 → 后果：勾 9 个工程一键释放后 banner 只说"N 项被安全护栏拦下"，3 秒自动消失，用户不知道是哪几项、是否因为自己加过白名单。文档承诺超出了实现。
- 处置：**本轮修一半**——把确认框与 README 的措辞改成兑现后的描述（"源码、被白名单保住的目录、无权限删除的项都会原样留下，并在结果里分列各类数量"，与 `Outcome.summary` 实际分列 `needsPrivilege`/其它拦下/删除失败一致）。**逐项列表转下一轮**，见文末待议。

### [P2] 行级「释放产物」不受 `isCleaning` 约束 → 并发删除任务把网关记账挤成无锁读改写，丢历史与撤销记录

- 位置：`DevProjectRow.cleanActionButton` 的 disabled 条件缺 `isCleaning`；根因 `ResidueDeletionGate.record` 的 `load → insert → save` 全程无锁
- 症状 → 后果：连点几行即并发投递多个 `execute`。删除各有护栏不会误删，坏在记账：后写者把前一个的记录整份覆盖，**用户刚清掉的一项既进不了历史也没有撤销快照**，而界面 `cleanedCount` 看着完全正常——正好把本轮要兑现的"清完有回退路径"静默破掉。
- 处置：**已修**。① `record()` 整段套 `journalLock`；② 两个清理入口加 `guard !isCleaning`；③ `DevProjectRow` 增 `isCleaning` 并纳入行内按钮 disabled；④ 新增网关级并发断言（8 路并发清理后，本轮 8 条历史与 8 份撤销快照必须一条不少）。
- 变异验证：撤掉 `journalLock` → 新断言**连续 3 次全红** ✔（不是偶发抢跑）。

### [P3] 两处 `selected.contains(candidate.path)` 是恒真护栏（删掉它 570 全绿）

- 位置：`DevProjectScanner.cleanOutcome`、`PreferenceResidueInspector.cleanOutcome`
- 症状 → 后果：`selected` 就是由同一批 candidates 生成的集合，guard 的 else 永不可达。危害是它**读起来像一条"只删本轮勾选项"的安全护栏**，后来的人会把真正的准入压到它下面。
- 处置：**已修**，两处各删 5 行。真正的准入来自调用方的 `filter(\.isSelected)` 与网关本身。

### [P3] `real == derivedDataRoot` 把"删掉 DerivedData 根本身"放进授权范围，与同轮偏好模块口径相反

- 位置：`DevProjectScanner.cleanOutcome` 的 `underDerivedData`
- 症状 → 后果：G14 明文"永不授权删域根本身"，偏好侧照做（等号缺席），开发侧多写 `real ==`，于是整棵 `~/Library/Developer/Xcode/DerivedData` 在范围内。当前扫描器只产子项所以今天打不响，但这条 policy 是模块侧唯一那道判据，留着等号等于在网关外留了一个"根可删"的口径。
- 处置：**已修**，去掉等号。断言走**源码形态**（`!contains("real == derivedDataRoot")`）而非行为——拿真实 DerivedData 根做行为断言，一旦判错就是把用户整棵构建目录删掉，不能这么测。变异验证：把等号加回去 → 该断言变红 ✔。

### [P3] `home:` 形参看着像"可换主目录"，实际网关只认真实主目录 + `/tmp` + `/var/tmp`

- 位置：`PreferenceResidueInspector.preferenceRoots(home:)` / `cleanOutcome(home:)`
- 症状 → 后果：传非默认 `home` 时模块自己的 roots 判据放行、网关一律回 `blockedByBaseGate`，即"参数可用但恒失败"，报出来是一句含义模糊的拒绝。自检夹具恰好在 `/tmp` 下，把这个不一致挡住了。
- 处置：**不修本轮**（改签名要连 `scanOrphanPreferences(home:)`、`Uninstaller` 调用点与两个自检一起动，且"本模块到底支不支持换 home"是产品决策）。转下一轮，见待议。

### [P3] 又往 `body` 里加了一趟全表 reduce，未按清单"算一次再向下传"

- 位置：`DevProjectInspectorView` 新增的 `totalSelectedCount`，与 `totalSelectedSize` 被 4 处引用
- 症状 → 后果：每次 body 求值扫 5 遍全表，且 `DevProject.selectedArtifactSize`/`isPartiallySelected` 各自 `filter()` 分配中间数组。9 个工程时打不出来，上百个工程时每次勾选都重算 5 遍。
- 处置：**已修**。`DevProject.selectedSummary` 一趟算出体积+条数（`reduce(into:)`，免中间数组）；卡片 `body` 开头把 `filteredProjects` 与 `selectedTotals` 各算一次，`projectListView` / `bottomActionBar` 改为接收参数。

## 待议（转下一轮）

1. **逐项呈现网关拒绝原因**：`Outcome.rejected` 已带 `name/path/reason/message`，但 DevProject 卡片与
   偏好面板都只取聚合计数。参照 `DiagnosticReportScanner.lastRejected` 的做法在卡片里列一个限高列表
   （`needsPrivilege` 与 `userWhitelisted` 要分开说——白名单项得明说"是你自己保住的"）。改完必须真机看版面。
2. **`PreferenceResidueInspector` 的 `home:` 语义**：要么收掉参数（内部固定 `NSHomeDirectory()`），
   要么让 roots 判据也走网关同一入口。现状是"能传但恒失败"。
3. **非网关写入口的读改写仍未串行**：本轮只给 `ResidueDeletionGate.record` 上了锁。
   AppState、AutoCleanService、下载归档、截图归档、硬链接去重这 5 个写历史的调用方仍是各自
   `load → insert → save`，互相之间以及**与网关之间**仍可能覆盖。根治要把原子写入下沉成
   `HistoryStore.append(_:)` 单一入口。
4. **源码接线自检只有 5 个模块**：其余 12 个 `ResidueDeletionGate.execute` 调用方靠人工 grep 维持。
   可考虑改成一条遍历全模块文件的通用断言（但要先解决"注释里提到被禁 API 就撞红"的误报问题）。
