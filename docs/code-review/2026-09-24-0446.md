### P1 — 重要

- **`Sources/MacClean/ResidueDeletionGate.swift:225`**（并连带 `HardlinkDedupService.swift:415`、`HardlinkDedupService.swift:469`、`AutoCleanService.swift:115`、`DownloadsOrganizerScanner.swift:303`、`ScreenshotsOrganizerScanner.swift:326`）— 5 个写入口丢弃了 `HistoryStore.append` 的返回值，`AppState.history` 内存缓存不刷新
  - 为什么是问题：`AppState.history`（`AppState.swift:101` 启动时读一次盘）是 **`HistoryView`、`DashboardView`、`SidebarView` 计数、`SearchView` 的唯一数据源**——这四处都直接读 `app.history`，没有任何 `onAppear`/`onChange` 会重新读盘（已 grep 确认：全仓 `history = HistoryStore.load()` 只有 `AppState.swift:101` 一处，`HistoryView` 无 `onAppear`/`task`）。只有 `AppState.swift:694` 的 `recordClean` 消费了返回值。于是：**从任一治理卡片（ColorSync / 打印机驱动 / 音频 HAL / 多语言瘦身 / 剪贴板 / 诊断报告 / 启动项残留 / 下载归档 / 截图归档 / 开发工程产物 / 偏好碎片）清一次，切到「清理历史」页看不到这条记录，侧栏计数也不变**；只有再回主界面点一次「清理已选项」或重启 App 才会出现。旁证：`MenuBarView.swift:672` 是直接 `HistoryStore.load()` 读盘的，所以菜单栏的周释放量是新的、主窗口是旧的——同一份数据两个视图不同步。本轮修的正是「历史被无声抹掉」，但只修了**丢数据**这一半，**显示滞后**这一半没修，而且项目自己的 `docs/RELEASE-CHECKLIST.md` 新增判据 ② 写的就是「内存缓存只能由该入口的返回值刷新」——现在只有 1/6 个入口满足。无数据丢失（盘上是全的、重启可见），故定 P1 而非 P0。
  - 建议：三选一即可闭环。① 给 `AppState` 加一个 `refreshHistory()`（`history = HistoryStore.load()`），让这些路径清完调一次；② 让 `HistoryStore.append` 发一条 `NotificationCenter` 通知，`AppState` 订阅后刷缓存（写入方零改动，最省）；③ 最省事的兜底：`HistoryView` 加 `.onAppear { app.history = HistoryStore.load() }`。另建议在 `Selftest+SystemAndHistory.swift` 现有的那条反证上补一个用例：**经 `ResidueDeletionGate` 写一条，断言 `app.history` 也包含它**——现有用例只覆盖了 `recordClean` 这一条路径，所以这个缺口是绿的。

### P2 — 建议

- **`Sources/MacClean/UndoSnapshot.swift:174-175`** — 对局部 `session` 的赋值已成为**死写**
  - 为什么是问题：`restore` 现在把「哪些项放回成功」攒进 `restored: [(index, path)]`，最后在 `mutate` 闭包里重新读盘落账（第 189-196 行），落账来源是 `restored` 而不是局部 `session`。第 174-175 行仍在对局部副本写 `isRestored`/`restoredPath`，但这个副本此后不再被读（第 140 行的 `guard` 每个下标只访问一次），也不再有 `sessions[idx] = session; save(sessions)` 把它写回。值恰好一致所以当前无害，但读代码的人会以为「这段循环已经持久化了」——将来若有人据此把 `mutate` 那段删掉，落账就真没了。
  - 建议：删掉 174-175 两行，让 `restored.append((i, destPath))` 成为唯一的「已成功」记录；或在 174 行上方补一句「此处只更新局部副本，落账在下方 `mutate` 里重新读盘完成」。

- **`Sources/MacClean/History.swift:83-86`** — `append` 在锁外二次读盘，一次追加读两遍
  - 为什么是问题：`mutate` 返回时 `transactionLock` 已由 `defer` 释放，随后第 85 行的 `return load()` 是在**锁外**执行的。方向上是安全的（只会读到比本次写入更新的内容，不会更旧），所以不是 bug；但它意味着 `append` 每次都要完整读一遍 `history.json`（200 条记录），并且留下一个「锁外读共享状态」的形状——后人很容易在这个位置扩出一段真正不安全的逻辑。
  - 建议：让 `mutate` 把落盘后的数组回传（`private static func mutate(_ body: ...) -> [CleanRecord]`，`defer` 释放锁前 `return records`），`append` 直接用它，省掉一次读盘也消掉锁外访问。

- **`Sources/MacClean/Selftests/Selftest+SystemAndHistory.swift`**（新增的源码不变量用例，`files.count > 110` 那条）— 用文件数下界守卫扫描范围，余量偏紧且报错信息会指向错误方向
  - 为什么是问题：实测命中 117，下界 110，只有 6% 余量；本项目正在活跃重构（本窗口就有模块收编、文件重排），删/并 8 个源文件就会撞红，而失败信息打的是「扫描范围没铺开」——会把人往错误方向带（真因是项目变小了，不是扫描坏了）。
  - 建议：把「范围是否铺开」改成**断言扫描结果里包含若干已知文件名**（如 `AppState.swift`、`Cleaner.swift`、`History.swift`），这能精确区分「范围没铺开」和「项目变小了」；计数下界可保留但放宽（如 `> 80`）或直接删掉。

## 附：与任务书的口径冲突（本轮首次真正踩到，需用户裁决）

`scripts/scan_projects.py` 的 docstring 要求 `last_review` 写「**已覆盖文件中最老的 mtime**」，而任务书第 4 步要求写「**本轮扫描时间**」。两者在「有截断 + 有 commit」时互斥：

- 写**扫描时间**：被 `--max-files` 砍掉、且**已提交**的文件（`git status` 不再显示、只能靠 mtime 进变更列表）会**永久失联**。
- 写**最老 mtime**：本轮已覆盖的内容下轮会被重复列出，重复审查。

本轮 MacClean **正是这个组合**（截断 1 个 + 含已提交的 `0644aae`），本轮按任务书写的**扫描时间**。之所以安全，是因为本轮恰好把 16 个文件**全部覆盖**（含被截断那个），没有文件因之失联。**但这个安全性是巧合、不是机制**——建议二选一固化成规则：(a) 把 `--max-files` 提到能容纳单项目全量变更，或 (b) 让扫描器在 `truncated > 0` 时输出「本轮已覆盖的最老 mtime」供 `last_review` 使用，并把该值写进 JSON 而不是让任务自己算。
