## 发现与处置

### [P0] 外接盘迁移的 ditto 参数被 ditto 自身拒绝：迁移恒失败，且失败分支删掉目标卷上**与本次操作无关的既有目录**

- 位置：`SpaceArchiveService.swift`（迁移的 `SafeProcess.run` 参数、失败分支的 `removeItem`）
- 症状 → 后果：`ditto --sequesterRsrc <src> <dst>` 只在 PKZip（`-c -k`）形态下合法，纯复制时 ditto
  在解析参数阶段就退出（`ditto: --sequesterRsrc is only for PKZip archives`，exit 1，一个字节都不复制）
  ——**"迁移到外接盘"这个功能此前从来没有成功过一次**。而它必然走进失败分支，那里的
  `try? fm.removeItem(atPath: destPath)` 无条件执行，`destPath = 目标卷/<源 basename>`
  既没做重名唯一化也没过任何护栏（`isSafeToArchive` 只作用于源）。用户外接盘上若已有同名目录
  （自己拷过的旧副本），点一次"迁移"就把它**永久删掉**（不进废纸篓）。
  审查者用真实调用复现：预置 `vol/src/PREEXISTING.txt` 后迁移，`srcStillThere=true` 而
  `preexistingDestStillThere=false`，同时整套自检 573 全绿。
- 处置：**已修**。① 复制形态去掉 `--sequesterRsrc`（`ditto` 的复制形态本身就保留
  resource fork / ACL / xattr，实测去 flag 后 exit 0 且内容完整落位）；② 新增
  `uniqueDestination(in:named:)`，落点保证未被占用（与归档侧 `generateUniqueZipPath` 同形），
  于是失败分支只可能删到本次新建的那一份；③ 补一条**真跑 ditto** 的行为自检。
- 修后变异验证：把 `uniqueDestination` 退回拼死路径 → 新自检变红 ✔。

### [P1] 「G15 不变量：全仓…」其实只扫顶层目录，`Rules/` 与 `Selftests/` 共 57 个文件不在范围内

- 位置：`Selftest+DeletionGate.swift`（`contentsOfDirectory(atPath:)` 不递归）
- 症状 → 后果：`contentsOfDirectory` 只返回顶层，实测往 `Rules/CleanupRules.swift` 放一个真
  `Process()` 仍然 573 全绿——正是清单里"看起来在把关，其实一直在空转"那个形状。
  另外那个排除 `"Selftest+DeletionGate.swift"` 的条件永远匹配不到任何文件（死代码），
  是实现者以为自已扫进了 `Selftests/` 的铁证。
- 处置：**已修**。改 `subpathsOfDirectory`，显式跳过整个 `Selftests/` 子树（自检代码里就有
  `"Process()"` 这个字面量，且不进发布产物），并把文件数下界断成 `> 100`（"扫到 0 个文件"
  不能伪装成"零违规"）。check 标题与 `docs/CLEANUP-RULES.md` 的"全仓"改成"产品源码全子树"。
- 修后变异验证：往 `Rules/CleanupRules.swift` 放真 `Process()` → 该不变量变红并打印
  `Rules/CleanupRules.swift:669` ✔。

### [P1] 新自检对**唯一会删原件的迁移路径**零覆盖：把"失败时删用户原件"写进去，仍然全绿

- 位置：`Selftest+SpaceArchiveDeep.swift`（迁移那条用 `_ =` 丢掉返回值，只回看注入桩记的参数）
- 症状 → 后果：只断言"参数长什么样"，从不断言"这件事做成了没有"。审查者实测：在迁移失败分支
  加一行 `removeItem(expanded)`（每次失败就永久删用户原件，文案还写着"原件未移动"）→ 573 全绿；
  把同一行放进归档分支 → 立刻红。同一个 P0 级动作，放归档红、放迁移绿。
- 处置：**已修**。新增「外接盘迁移真的把文件复制过去，且绝不碰目标卷上已有的同名目录」——
  不注入、真跑 ditto，断言 `success`、文件确实落到目标卷、既有同名目录里的用户文件原样还在、
  且本次内容没被混进那个目录。

### [P2] 超时断言用 `>= 600` 而线上值是 3600：有人把常量缩到 15 分钟照样绿

- 处置：**已修**。改成 `== SpaceArchiveService.dittoTimeout`，并在 check 顶部加
  `dittoTimeout >= 30 * 60` 的绝对值断言。变异验证：常量改 15 分钟 → 红 ✔。

### [P2] 注入桩同时给 `exitCode: -1` 与 `timedOut: true`，使 `!ditto.timedOut` 这个新守卫不可证伪

- 处置：**已修**。超时用例改注 `Result(exitCode: 0, output: "", timedOut: true)`
  （被 SIGTERM 后自己干净收尾是真实存在的形状）。变异验证：删掉 guard 里的 `!ditto.timedOut`
  → 红 ✔（此前是绿）。

### [P2] 60 分钟定值 + 无取消通道

- 处置：**本轮不修，转待议**。数据安全侧无后果（超时/失败都不动原件，已实测），
  坏在可用性：慢速 USB 卷上 >90 GB 的迁移会以"超时"收场；跑满一小时期间界面转圈与按钮禁用
  不会提前解除，且没有取消入口。加取消要动 `SafeProcess` 公共签名并被 11 个调用方共享。
  已把这两条限制如实写进 README 的功能段（不再只说"已硬化"）。

### [P3] 接线断言用了与工作目录耦合的 `SelftestSource.read` 兜底；且不跳注释行

- 处置：**已修**。改用 `Selftest.sourceDirectoryPath` 绝对路径直读（读不到即判失败），
  并改成逐行扫描、跳过 `//`/`///`——本仓库习惯在注释里写"此前是裸 `Process()`"，
  整文件子串匹配会被自己的注释撞红。验证：在该文件加一条含 `Process()` 字面量的注释 →
  该 check 仍然绿 ✔（不误报）。
