### P1 — 重要

- **`Sources/MacClean/Uninstaller.swift:595`（`size: FileSystem.size(at: child)`，`child` 来自 `:580-581` 的 `children(of: "/Applications").filter { $0.hasSuffix(".app") }`）** — 本轮新增的「包内口径」（`bundleSize`）**只接到了 2 个调用点**（`AppLocalizationScanner` 3 处、`DownloadsOrganizerScanner:81`），而**卸载器**——按 `.app` 求体积最直接、最显眼的消费方——仍走粗口径 `FileSystem.size`。
  - 为什么是问题：`FileSystem.size` → `measure(descendIntoPackages: false)` → `options: [.skipsPackageDescendants]`，会跳过 `.app` 内**嵌套包**（`Contents/Frameworks/*.framework`、`Contents/PlugIns/*.appex`、`Contents/Helpers/*.app`）的全部内容；而 `bundleSize` 的 doc comment（`:569-571`）自己写着这个差值「**少算 3%~35%**」。于是**同一个 App 在两个面板显示两个数**：应用本地化面板用 `bundleSize`（对），卸载器用 `size`（偏小）。`Uninstaller.swift:584-587` 的注释还专门交代了「每个 `.app` 的体积都是一次全量递归…本机 28 个第三方 App 实测 2013 ms」，说明这里本来就该是"App 的真实占用"。
  - 判定依据（可复核）：① 新自检 `Selftest+DownloadsOrganizerDeep.swift` 里那条「两种求体积口径不得共用缓存」断言 `fineFirst > coarseFirst`，即对**以 `.app` 为根**的路径 `bundleSize > size`，这是项目自己的实测结论；② `size` 与 `bundleSize` 对非包目录给出同一个数（同一条自检的注释：「实测裸 `Inner.framework/Versions/A/Resources/` 不算包，两种口径给出同一个数」）——所以差异**只**来自包内嵌套包，正是 `.app` 的形态。
  - 同类位置（同一根因，建议一并核）：
    - `Cleaner.swift:52`（`let actual = FileSystem.size(at: target)`，删除前实测用于记账）——目标若是 `.app`，则「已释放」少报；
    - `ResidueDeletionGate.swift:166`（同上，`删除前实测真实体积`）；
    - `DownloadsOrganizerScanner.swift:285`（`let actual = FileSystem.size(at: realSrc)`，**移动前实测**）与同文件 `:81`（列表用 `bundleSize`）**在同一条流程里用了两个口径**——面板显示的体积与「已归档 X GB」的记账会不一致；
    - `PluginExtensionInspector.swift:274`（插件/扩展目录，多为 `.appex`/`.bundle`）。
  - 建议：把「求 `.app`/`.pkg`/`.appex`/`.framework` 体积」收敛成一个入口——要么给 `FileSystem.size` 加一层「根是包时自动下钻」，要么把上列位置逐个改成 `bundleSize`；并在 `size(at:)` 的 doc comment 上显式写「**根是包时不下钻嵌套包，对 `.app` 会少算**」（现在这条约束只写在 `bundleSize` 那一侧，`size` 的注释 `:710` 一个字都没提）。

- **`Sources/MacClean/FileSystem.swift:613-614`（`incompleteWalks` 的读—删）** — 「被权限挡过的结果不写跨会话缓存」这条不变量在**并发下不成立**：标志是一张按 session key 索引的**全局副表**，而消费它的是"**第一个**跑完 `computeMeasurement` 的调用方"。
  - 交错（两条线程同时测同一路径 P，且两次遍历都被挡）：
    1. A：会话缓存未命中 → `computeMeasurement(P)` → errorHandler 触发 → `incompleteWalks.insert(K)`（`:659`）
    2. B：同样未命中 → 同样 `insert(K)`（已存在，无操作）
    3. A 先跑完：`:613` 读到 `contains(K) == true` → `:614` **remove(K)** → `:620` 跳过 `IncrementalCache.update` ✅
    4. B 后跑完：`:613` 读到 `contains(K) == false`（被 A 删掉了）→ `:620` **照常 `IncrementalCache.update(at: P, measurement: 部分值)`** ❌
  - 为什么是问题：写进去的是**残缺体积**，而 `IncrementalCache` 的指纹只看目录自身 `lstat` 与顶层子项数——chmod 前后这两者都不变，于是这个偏小的数会被当权威值复用**最长 7 天**。这正是本段注释（`:617-619`）与 `CLEANUP-RULES.md` 里「免得一个残缺值被当权威值复用最长 7 天」要消灭的那一个，也是 §7.2 的形状。
  - **可达性（未实测，由并发结构推演，请项目侧确认）**：`Scanner.scanAllCategories` / `scanAllCategoriesWithProgress` 用 `DispatchQueue.concurrentPerform(iterations: 6)`（`Scanner.swift:308`/`:338`），`Scanner.swift:134` 的注释写着「`scanAll` 会并发地把 6 个分类一起丢进来（各自 `DispatchQueue.global`）」；`Scanner.swift:272` 的注释又明确「同一轮里 `Application Support` 还被两个分类共用」。UI 侧 `AppState` 的扫描在 `DispatchQueue.global(qos: .userInitiated)`（`AppState.swift:289`），而 `SpaceVisualizerModel.expandDirectory` 在主线程对同一批目录逐个调 `FileSystem.size`——两者可以叠在同一路径上。**我没有插桩复现**，只确认了并发结构与共享路径都存在。
  - 建议：把标志从副表改成**返回值**——`computeMeasurement` 返回 `(Measurement, walkBlocked: Bool)`，`measure` 直接用它决定要不要写 `IncrementalCache`。这样语义随调用走，与并发无关，`incompleteWalks` 这张表和它的三处 insert、三处 remove（`:498/504/613-614/659/668/690`）可以整块删掉。顺带修掉一个现有小瑕疵：`:668` 在包内口径下多插了一个裸 `cacheKey(path)`，`measure` 只消费 `key`（带后缀），那条裸键会一直留到下一次 `beginMeasurementSession()`，让后续粗口径的 `measure` 平白跳过一次指纹缓存写入（方向是保守的，只损失缓存命中，不产生错数）。

### P2 — 建议

- **`Sources/MacClean/FileSystem.swift:535`（`sampleMeasurement` 的 nil-enumerator 分支）** — 仍在用 `isPermissionDenied(path)` 当记账门槛，而本轮刚在 `computeMeasurement` 的**同一形状分支**上论证过这个门槛是错的、并改成了无条件记账（`:670-678` 的注释：「枚举器返回 nil 本身就是一手失败证据。而 `isPermissionDenied` 在"在途额度已满、这次根本没去 open"时返回 false，于是这条真实失败会被漏记」）。
  - 为什么是问题：同一文件里对同一件事给出两条相反的判据。`usageMeasurement` → `sampleMeasurement` 是聚合型清理项（`~/.m2/repository`、`~/Library/Caches`）每次都要走的路，若枚举器返回 nil 且当时在途额度已满，这次失败不会进盲区清单。影响有界（作者自己在 `:674` 写「实测这条分支在本机几乎不可达」），但两处口径不一致会让下一个人不知道该照哪一处改。
  - 建议：与 `:678` 对齐，改成无条件 `noteDeniedRoot(normalizePath(path))`（保留 `recordDeniedAccess` 也无妨，`noteDeniedRoot` 自身幂等）。

- **`Sources/MacClean/FileSystem.swift:414`（`recordBlindSpotIfNeeded` 用 `lstat` 判类型）** — 连续第 2 轮，见上「上轮遗留项验收」。本轮 `isPermissionDenied`（`:1005-1013`）也改成了委托 `probeDirectory`（走 `stat`），于是 `recordBlindSpotIfNeeded` 成了全文件**唯一**用 `lstat` 判目录类型的地方，与 `:344-348` 的显式结论直接冲突。
  - 为什么是问题：影响有界（3 个调用点后面都紧跟 `isReadableWithDeadline`，软链情形会被第二道拦住），但①同一文件对同一件事两条相反判据，②这个函数还被性能自检直接当作"探测能力"的代表来量（`Selftest+Performance.swift:361`）。
  - 建议：换成 `stat`，或直接删掉类型判定、委托 `probeDirectory`（`== .readable`），让「该用什么原语」只有一处定义。

- **`Sources/MacClean/FileSystem.swift:164-166`（`noteDeniedRoot` 迭代 `deniedRoots.keys` 时 `removeValue`）** — 连续第 2 轮。目前**是安全的**（`Dictionary.Keys` 视图持有旧 buffer，写时复制让迭代跑在旧快照上），但这是靠语言实现的巧合而非意图；同文件 `deniedAccessSnapshot()`（`:191`）处理同一件事时用的是 `let all = Array(deniedRoots.keys)` 先取快照。
  - 建议：改成 `for existing in Array(deniedRoots.keys)`，与 `deniedAccessSnapshot` 统一。
