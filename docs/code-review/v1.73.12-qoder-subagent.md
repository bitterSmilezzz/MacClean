## 1. 本轮先做了什么、为什么又收回

原判断：面板用 `directoryStats`（跳隐藏、下钻 `.app` 包）、删除侧记账用 `measure`（不跳隐藏、
**不**下钻包），两者对同一棵树给出两个数，实测方向不固定（含包目录的缓存树面板多约 1.06 GB，
含隐藏项的容器树少约 67 MB）。于是尝试"改记账侧"：网关删目录时改用 `directoryStats`，
使"面板承诺量 = 历史记录量"。

**复审 E-P1-1 驳回**：`DevProjectScanner`（8 处）、`PluginExtensionInspector`、
`DownloadsOrganizerScanner`、`AppLocalizationScanner`、`PreferenceResidueInspector` 这些分类的
面板体积本来就走 `size`/`bundleSize`——今天它们是"面板 = 记账"，一刀切会把它们从一致切成不一致
（含包目录时**记录反而大于承诺**，比原问题更刺眼）。
**已回退**，并把这条不变量反向钉成自检：

> `删除网关：面板走 size 的分类，记账必须仍等于面板那个数（不许一刀切换口径）`
> 夹具：一棵含 2 MB `.app` 包内容的目录，面板口径 1,003,520 / 目录口径 3,006,464。
> 变异 M25（把网关换成 `directoryStats`）→ 判红，报出"记账 3006464 ≠ 面板当初那个数 1003520"。

`FileSystem.directoryStats` 的 doc 与 README 同步改口：不再宣称"记账已同源"，而是写明
**统一必须逐模块做**（任务 #15 仍开放，需要产品决定每个分类的"可清理"到底按哪个口径承诺）。
